# Design

## Context

See proposal.md (Why). Current state that shapes the approach:

- `.github/workflows/release.yml` runs on `v*.*.*` tags. `verify` checks the tag and runs
  typecheck and tests. Then two jobs run in parallel: `release` (`contents: write`) runs
  `gh release create --verify-tag --generate-notes`, adding `--prerelease` for a `-` tag;
  `image` (`packages: write`) builds `linux/amd64,linux/arm64` with
  `docker/build-push-action@v7` and pushes `ghcr.io/emmpaul/elegoo-centauri-carbon:X.Y.Z`
  (and `latest` for stable tags). The workflow-level permission is `contents: read`.
- The `image` job does not expose the pushed digest today. `build-push-action` has a
  `digest` output for the multi-platform index.
- Actions are pinned by major tag; Dependabot updates `github-actions` weekly and
  auto-merges minor and patch updates.
- The GHCR package is private by default until the user makes it public
  (`docs/deployment.md`), so reading the image back in CI needs a registry login.
- The image is `node:26-slim` (Debian) plus `node_modules` from
  `pnpm install --prod`, which is empty today but must be covered when a dependency is
  added.

## Goals / Non-Goals

**Goals:**

- The SBOM describes exactly the image pushed by the same run (by digest, not by a tag
  that could move).
- A failed SBOM step never blocks or undoes the image push or the release; it shows as a
  failed job on the release run.
- Re-running the failed job finishes the job without duplicating anything.

**Non-Goals:**

- A local `pnpm` script to generate SBOMs. Contributors can run `syft` against
  `ecc:dev` by hand; the tasks do that once to check the output.
- Changing the order of `release` and `image`, or making the release wait on the image.

## Decisions

### D1. Generate with Syft from the pushed digest, in a separate job

A new `sbom` job with `needs: [release, image]` installs Syft with
`anchore/sbom-action/download-syft@v0`, logs in to GHCR with `packages: read`, and runs,
for each of `linux/amd64` and `linux/arm64`:

```
syft scan registry:ghcr.io/emmpaul/elegoo-centauri-carbon@<digest> \
  --platform <platform> -o spdx-json=elegoo-centauri-carbon-<version>-linux-<arch>.spdx.json
```

`<digest>` is the multi-platform index digest, exposed as a job output of `image` from
the `build-push-action` step (`steps.build.outputs.digest`). Syft resolves the platform's
manifest from the index.

Scanning the pushed image, rather than the build context or lockfile, captures the base
image's Debian packages and the Node binary as well as npm packages, which is what a
CVE check needs.

*Alternatives considered:*

- **BuildKit SBOM attestations** (`sbom: true` on `build-push-action`), then extracting
  them with `docker buildx imagetools inspect --format '{{ json .SBOM }}'`. It also
  attaches the SBOM to the image in the registry, but it changes what the `image` job
  pushes (extra attestation manifests that GHCR shows as `unknown/unknown` platforms),
  produces in-toto-wrapped SPDX that needs unwrapping, and ties SBOM failures to the
  image push. Kept as a later option; out of scope here.
- **`anchore/sbom-action` itself** (rather than only its `download-syft` sub-action). It
  uploads release assets only on `release` events and has no per-platform naming, so the
  workflow would still need its own upload step. Running Syft directly keeps the
  commands visible and testable locally.
- **SBOM from `pnpm-lock.yaml`** only: misses the OS packages and the runtime.

### D2. SPDX JSON, one file per platform

SPDX JSON is Syft's most widely consumed output and what GitHub's dependency graph
imports. One file per platform because the arm64 and amd64 images have different Debian
package builds and Node binaries; a merged document would hide which is which.

### D3. Upload with `gh`, append notes idempotently

The `sbom` job's permissions are `contents: write` (assets and notes) and `packages: read`
(pull from GHCR); nothing else. It checks out nothing: the job needs no repository files.

1. `gh release upload "$GITHUB_REF_NAME" <files> --clobber` so a re-run replaces the
   assets.
2. Read the current notes with `gh release view --json body -q .body`. If they already
   contain the marker line `<!-- sbom -->`, cut everything from the marker on; then
   append the marker and the section, and write it back with
   `gh release edit --notes-file`. The generated notes above the marker are left as they
   are.

The section names the image as `ghcr.io/emmpaul/elegoo-centauri-carbon@<digest>` with the
`X.Y.Z` tag, links each asset at
`https://github.com/<repo>/releases/download/<tag>/<file>`, and states
"SPDX 2.3 JSON, generated by Syft <version>" (`syft version -o json`).

`needs: [release, image]` is what makes this safe: the release exists to edit, and the
digest exists to scan. Because `release` and `image` stay parallel, a failed `sbom` job
leaves a published release and image without the SBOM; the job is re-run on its own.

### D4. Shell lives in the workflow

The steps are a few lines of bash with `set -euo pipefail`, in line with the existing
`Image tags` and `Create GitHub release` steps. The notes edit is the only logic worth
checking, and it is checked by running the same snippet locally on a sample body (tasks).

## Risks / Trade-offs

- [A new third-party action with `contents: write` in the same job] → It only downloads
  the Syft binary; pin `@v0` like the other actions and let Dependabot propose updates.
  Job permissions are the minimum listed in D3.
- [Syft output changes between versions] → The notes record the Syft version; the spec
  only fixes the format and file names.
- [The release is visible for a minute or two without the SBOM] → Acceptable; the section
  appears once the job ends. The release skill's watch step waits for the whole run.
- [`--clobber` replaces assets on re-run] → Intended for this job's own files only; the
  file names are specific to the SBOM.
- [Editing notes races a manual edit by the user during the run] → Unlikely in a
  single-maintainer repo; the edit keeps everything above the marker.

## Migration Plan

Merge the workflow change, then cut the next release (a prerelease such as
`v1.0.0-rc.4` is enough) with `/release` and check the assets and the notes. Rollback is
reverting the workflow commit; an existing release keeps its assets and notes unless they
are deleted by hand. Past releases do not get SBOMs.
